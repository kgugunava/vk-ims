# msgfmt

Библиотека и консольная утилита на C++17, которые превращают сообщение с разметкой в пару «чистый текст + стилевые диапазоны» — так форматирование передаётся в Bot API мессенджеров. Позиции диапазонов считаются в кодовых единицах UTF-16.

```
$ printf 'Привет, **мир**!' | msgfmt
{"text":"Привет, мир!","ranges":[{"style":"bold","offset":8,"length":3,"url":""}]}

$ printf '2 * 3' | msgfmt escape
2 \* 3
```

Поддерживаются `**жирный**`, `_курсив_`, `` `код` `` и `[ссылка](url)`, вложенность разных стилей и экранирование обратным слешем. Только стандартная библиотека, без сторонних зависимостей.

## Сборка и тесты

Команды из задания:

```bash
cmake -S msgfmt -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
ctest --test-dir build
```

Опции CMake:

| Опция | По умолчанию | Что делает |
|---|---|---|
| `MSGFMT_SANITIZE` | `OFF` | ASan + UBSan с `-fno-sanitize-recover=all`, чтобы UBSan завершал тест с ошибкой, а не только печатал сообщение |
| `MSGFMT_WERROR` | `OFF` | Предупреждения как ошибки. Выключено по умолчанию: новая версия компилятора может добавить предупреждение, и чужая сборка не должна из-за этого ломаться |
| `MSGFMT_TEST_ASAN_OPTIONS` | `detect_stack_use_after_return=0` | `ASAN_OPTIONS` для тестов (см. «Санитайзеры») |

Сборка с санитайзерами и одним тестом:

```bash
cmake -S msgfmt -B build-asan -DCMAKE_BUILD_TYPE=Debug -DMSGFMT_SANITIZE=ON
cmake --build build-asan
ctest --test-dir build-asan --output-on-failure        # все тесты
ctest --test-dir build-asan -R msgfmt.parser           # один тест
ctest --test-dir build-asan -LE heavy                  # без тяжёлых тестов
```

Санитайзеры можно передать и через `-DCMAKE_CXX_FLAGS="-fsanitize=address,undefined"` — это тоже проверено.

### Полная проверка в Linux

Окружение проверки задания — Linux, поэтому всё проверяется в контейнере (`docker/dev.Dockerfile`: Ubuntu 24.04, GCC 13, Clang 18, CMake 3.28):

```bash
scripts/in-docker.sh ./scripts/check-msgfmt.sh
```

Шаги: clang-format → GCC и Clang в Release с `-Werror` → GCC и Clang с ASan + UBSan → GCC ASan с проверкой stack-use-after-return → команды из задания как есть (без наших опций и с санитайзерами через `CMAKE_CXX_FLAGS`). Сборка `-Wall -Wextra -Wpedantic -Wshadow -Wconversion -Wsign-conversion -Wold-style-cast` проходит без предупреждений обоими компиляторами.

### Санитайзеры

GCC 13 по умолчанию включает в ASan проверку stack-use-after-return, которая стоит около 10 мкс на каждый вызов функции: тест свойств шёл бы часами. Clang её по умолчанию не включает. Тесты получают `ASAN_OPTIONS=detect_stack_use_after_return=0` (как у Clang), а скрипт проверки отдельным шагом гоняет все тесты без метки `heavy` с включённой проверкой.

## Командная строка

```
msgfmt            < input    # разбор, JSON в stdout
msgfmt escape     < input    # экранирование служебных символов
```

| Код | Когда | stdout |
|---|---|---|
| 0 | успех | JSON (с переводом строки в конце) или экранированный текст (без добавленного перевода строки) |
| 2 | вход не является корректным UTF-8 | `{"error":"invalid_utf8"}` |
| 1 | неизвестная команда или лишний аргумент, ошибка чтения или записи | пусто, сообщение в stderr |

JSON выводится одной строкой; поля и их порядок — `text`, `ranges`; у диапазона — `style`, `offset`, `length`, `url`. В строках экранируются `"`, `\` и управляющие символы ниже U+0020, остальной UTF-8 выводится как есть.

## Устройство

```
include/msgfmt/msgfmt.hpp   API: Parse, Escape, StyleName; типы Style, Range, Message
src/utf8.*                  строгий декодер UTF-8, кодирование, длина в UTF-16
src/unicode.*               «буква или цифра» (L*, Nd) и «пробельный символ» (White_Space)
src/unicode_tables.inc      таблица Unicode 16.0, генерируется tools/gen_unicode_tables.py
src/markup.hpp              список служебных символов
src/parser.cpp              разбор
src/escape.cpp              экранирование
src/json.*                  вывод JSON
src/main.cpp                CLI
```

Поток данных: байты → `DecodeUtf8` (единственная ошибка — невалидный UTF-8) → разбор по кодовым точкам → текст в UTF-8 и диапазоны с позициями в UTF-16 → сортировка → JSON.

### Алгоритм разбора

Один проход слева направо (правило 1). Встретив открывающий маркер, парсер ищет его закрывающий маркер **внутри текущего региона**: всего входа или содержимого уже найденного стиля. Если пара найдена, содержимое разбирается рекурсивно как новый регион, в котором этот стиль отмечен открытым; если нет — маркер выводится как текст, а разбор продолжается со следующего символа. Код не разбирается рекурсивно: его содержимое копируется как есть (правило 7).

Из ограничения поиска регионом следует, что диапазоны всегда либо вложены, либо не пересекаются (правило 12). Сортировка — по `offset`, затем длинные раньше, затем по порядку открытия: номер присваивается до разбора содержимого, поэтому внешний диапазон идёт раньше вложенного при совпадении интервалов.

Правило 10 («маркер уже открытого стиля — текст») выполняется само собой: внутренний маркер того же стиля мог бы открыться, только если его пара лежит внутри региона, но тогда она была бы ближайшей парой для внешнего маркера. Проверка в коде оставлена как явное выражение правила; что она не меняет результат, подтверждено сравнением вывода с ней и без неё на всех строках до 9 символов над `*_a \` и до 8 над `[]()a \*` (21,6 млн входов).

### Линейное время

Наивный поиск пары для каждого открывающего маркера даёт O(n²) на входах вроде `**a **a **a …`: замер — 1 с на 64 КиБ, 4,3 с на 128 КиБ. Поэтому `CloserIndex` один раз строит для каждой позиции ближайшего кандидата в закрывающие маркеры каждого вида (`**`, `_`, `` ` ``, неэкранированная `]`, `)`, пробельный символ): может ли позиция закрывать, зависит только от неё самой, соседей и экранирования. Поиск становится обращением к таблице, разбор — O(n); вход 1 МиБ разбирается за ~0,2 с. Экранирование вычисляется одним проходом с начала входа; это совпадает с разбором пар `\X` от начала региона, потому что регион всегда начинается сразу после неэкранированного маркера. Старый и новый варианты дают одинаковый вывод на 12,1 млн входов.

## Принятые решения

Правила задания определяют поведение; там, где они допускают разные прочтения, приняты следующие решения.

| # | Вопрос | Решение |
|---|---|---|
| D1 | Пример 9 противоречит правилам 3 и 5 | Правила важнее примеров: `**жирный _и курсив_**` → bold(0, 15), **italic(7, 8)**. Единственный `_`, способный закрыть курсив, стоит перед `**`. Результат примера, italic(7, 1), получается из `**жирный _и_ курсив**` — в тестах есть оба варианта |
| D2 | Видит ли поиск закрывающего маркера вложенные конструкции | Нет: поиск текстовый в пределах региона, учитывает экранирование, но не пропускает вложенный код. `` **a `b** c` `` → bold на «a \`b» |
| D3 | Что выводится при неудачном маркере | Только сам маркер (`**` — оба символа); дальше разбор продолжается обычно: `[**a**]()` → `[a]()` с bold на `a` |
| D4 | Пустое содержимое (`****`, `__`, ` `` `) | Не стиль, а текст |
| D5 | Соседи для правила 3 | Соседний символ входа. Выбор между «концом региона» и «концом входа» не влияет на результат: регион всегда граничит с символом маркера |
| D6 | Правило 5 для `]` | Действует: `[a ](u)` — текст |
| D7 | `\]` в тексте ссылки | Допустимо: экранированный символ — обычный, `[a\]b](u)` → link на «a]b» |
| D8 | URL | Берётся как есть, без обработки экранирования; `(` допустима; первая `)` завершает URL |
| D9 | «Буква или цифра» | Категории Unicode L* и Nd (Unicode 16.0). Комбинирующие знаки не буквы, поэтому «й» из двух кодовых точек (и + U+0306) на границе слова ведёт себя иначе, чем «й» из одной — прямое следствие правил и запрета нормализации |
| D10 | «Пробельный символ» | Свойство Unicode White_Space (25 кодовых точек, включая NBSP) |
| D11 | Строгость UTF-8 | RFC 3629: overlong-формы, суррогаты, значения выше U+10FFFF, обрезанные последовательности — ошибка. NUL и BOM — обычные символы |
| D12 | Перевод строки в выводе | После JSON — есть; после `escape` — нет, чтобы вывод можно было снова подать на вход |
| D13 | Неизвестная команда | Код 1 (код 2 закреплён за невалидным UTF-8) |
| D14 | Экранирование JSON | `"`, `\`, короткие `\b \f \n \r \t`, прочие `< 0x20` — `\u00XX`; остальное как есть |
| D15 | Порядок полей JSON | `text`, `ranges`; `style`, `offset`, `length`, `url` |
| D16 | Одиночная `*` | Всегда текст |

Тесты написаны без фреймворков: небольшой раннер в `tests/test_util.hpp`, тесты CLI — через `tests/run_cli.cmake`.

**Тесты проверены на внесённых ошибках.** На каждом этапе разработки в код вносились типичные ошибки (около 80 за всё время) и проверялось, что тесты их ловят. Все ошибки, которые не были пойманы, оказались эквивалентными — не меняющими поведения ни на одном входе, — и это показано рассуждением или полным перебором.

## Известные ограничения

- Вход читается целиком и декодируется в массив кодовых точек; индекс закрывающих маркеров занимает 56 байт на кодовую точку (около 56 МБ на 1 МиБ ASCII). Для сообщений мессенджера это несущественно; при необходимости 32-битные индексы уменьшат его вдвое.
- Классы символов соответствуют Unicode 16.0; для другой версии таблица перегенерируется `tools/gen_unicode_tables.py` (берёт данные из модуля `unicodedata` используемого Python).
- Нормализация не выполняется (так требует задание), поэтому один и тот же видимый текст в разных формах Unicode может давать разные позиции и разные решения на границе слова (D9).
