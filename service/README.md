# ghreport

Консольная служба на Go: собирает JSON-сводку по открытым issue репозиториев GitHub. Корректно работает с постраничной выдачей, условными запросами (ETag), ограничениями частоты запросов и сбоями отдельных репозиториев. Только стандартная библиотека Go, без клиентских библиотек GitHub.

```bash
GITHUB_TOKEN=... go run ./cmd/ghreport --repos cli/cli,golang/go --limit 20 --out -
```

## Запуск

### Локально

```bash
cd service
go build -o ghreport ./cmd/ghreport
./ghreport --repos cli/cli --limit 20 --trace trace.jsonl --out -
```

### В Docker

```bash
docker build -t ghreport service/
docker run --rm -e GITHUB_TOKEN=... ghreport --repos cli/cli --limit 20 --out -
docker run --rm -e GITHUB_TOKEN=... -e GITHUB_API_BASE_URL=<адрес> ghreport --repos cli/cli --out -
```

Образ — `distroless/static` с пользователем `nonroot` (uid 65532), около 14 МБ. Токен и адрес API в образ не вшиты, оба передаются через `-e`. Рабочий каталог `/home/nonroot` доступен этому пользователю на запись, поэтому кэш по умолчанию (`./.ghreport-cache`) работает и в контейнере. Чтобы кэш переживал запуски контейнера, смонтируйте каталог: `-v "$PWD/cache:/home/nonroot/.ghreport-cache"`. Сервер на хосте доступен из контейнера как `host.docker.internal` (Docker Desktop) или через `--network host` (Linux).

### Флаги

| Флаг | По умолчанию | Описание |
|---|---|---|
| `--repos` | — | Обязательный список `owner/repo` через запятую; повторы удаляются, первое вхождение сохраняется |
| `--limit` | `100` | Максимум issue на репозиторий, не меньше 1 |
| `--since` | — | Только issue, созданные не раньше этой даты (`YYYY-MM-DD`, 00:00:00 UTC) |
| `--out` | `-` | Файл отчёта; `-` — стандартный вывод |
| `--trace` | — | Журнал HTTP-обмена в формате JSON Lines; без флага не ведётся |
| `--cache-dir` | `./.ghreport-cache` | Каталог кэша; создаётся автоматически |

Флаги принимаются в формах `--name value`, `--name=value` и с одним дефисом. Неизвестный флаг, лишний аргумент или повторённый флаг — ошибка.

### Переменные окружения

| Переменная | Назначение |
|---|---|
| `GITHUB_TOKEN` | Необязательный токен, отправляется как `Authorization: Bearer <token>`. Без токена GitHub разрешает 60 запросов в час |
| `GITHUB_API_BASE_URL` | Базовый адрес API, по умолчанию `https://api.github.com`. Завершающий слеш допускается, префикс пути сохраняется (`http://host/api/v3`) |

### Коды возврата

| Код | Ситуация | stdout |
|---|---|---|
| 0 | Все репозитории обработаны | отчёт |
| 1 | Часть репозиториев с ошибкой (или не удалось записать файл отчёта) | отчёт, у проблемных репозиториев заполнено `error` |
| 2 | Некорректные аргументы | пусто; сообщение в stderr |
| 3 | Ответ 401 или все репозитории с ошибками | `{"error":"unauthorized"}` или `{"error":"all_failed"}` |

В stdout попадает только отчёт или фатальный объект. Диагностика (повторы, паузы, ошибки репозиториев) пишется в stderr через `log/slog`. Токен не попадает ни в stdout, ни в stderr, ни в журнал, ни в кэш — это проверяется тестами.

## Пример вывода

```json
{
  "generated_at": "2026-10-25T13:42:58Z",
  "repos": [
    {
      "repo": "cli/cli",
      "error": null,
      "count": 1,
      "issues": [
        {
          "number": 136,
          "title": "Add better messaging to address archived repos",
          "author": "tierninho",
          "labels": ["enhancement", "core", "gh-pr"],
          "created_at": "2019-12-05T02:03:22Z",
          "url": "https://github.com/cli/cli/issues/136"
        }
      ]
    },
    {
      "repo": "example/missing",
      "error": "not_found",

      "issues": []
    }

```

Фатальные ошибки — одна строка: `{"error":"unauthorized"}`, `{"error":"all_failed"}`.

## Архитектура

```
cmd/ghreport/main.go     main → run(ctx, args, stdout, stderr, getenv): сборка, цикл по репозиториям, коды возврата
internal/cli             разбор флагов и окружения → Config
internal/ghapi           HTTP-клиент: запрос страницы, Link, повторы, лимиты, кэш, редиректы, журнал
internal/cache           ETag + тело ответа на диске
internal/trace           журнал --trace
internal/report          отчёт: маппинг полей, фильтры, дедупликация, сортировка, JSON
```

Поток выполнения: `run` разбирает аргументы, открывает журнал и кэш, затем для каждого репозитория по порядку вызывает `ghapi.Client.ListIssues`. `ListIssues` запрашивает первую страницу, отдаёт элементы сборщику (`report.Collector`) и переходит по `Link: rel="next"`, пока не наберётся `--limit` или не кончатся страницы. Каждую страницу получает `FetchPage` — один логический запрос со всеми повторами, паузами, перенаправлениями и условным запросом. Все запросы последовательные.

`main` и `run` разделены, чтобы CLI целиком тестировался без запуска процесса: аргументы, потоки и окружение передаются явно. Время и паузы в клиенте внедряются (`now`, `sleep`), поэтому тесты повторов и лимитов не ждут.

### Обмен с API

- Единственный эндпоинт: `GET {base}/repos/{owner}/{repo}/issues?state=open&sort=created&direction=asc&per_page=100`. Это единственный адрес, который служба строит сама: все следующие берутся из `Link: rel="next"` (относительные разрешаются относительно адреса запроса).
- Заголовки: `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2026-03-10`, `User-Agent: ghreport/1.0 (+https://github.com/kgugunava/vk-ims)` (GitHub отклоняет запросы без User-Agent), `Authorization: Bearer <token>` — только на хост базового адреса, никогда на другой хост из редиректа или `Link`.
- Таймаут одного запроса — 30 секунд, тело ограничено 64 МиБ.
- Pull request-ы исключаются по **наличию ключа** `pull_request` (даже со значением `null`).
- `--since` применяется к `created_at` на стороне службы: параметр API `since` фильтрует по `updated_at`.
- Повторы по `number` между страницами устраняются, побеждает первое вхождение.
- `--limit` отсчитывается в порядке выдачи; итог сортируется по `created_at` (как время, с учётом часового пояса), затем по `number`. `created_at` в отчёте — исходная строка API.
- Перенаправления 301, 302, 303, 307, 308 обрабатываются самой службой, а не `net/http`, чтобы каждый переход попал в журнал отдельной попыткой; не более 5 переходов.

### Ограничения частоты и повторы

| Ответ | Поведение |
|---|---|
| Сетевая ошибка, таймаут, 5xx | До 3 повторов с паузами 1, 2, 4 с; затем `request_failed` |
| 403/429 и признак лимита: `Retry-After`, `X-RateLimit-Remaining: 0` или сообщение о rate limit в теле | Пауза: `Retry-After` (секунды или HTTP-дата), иначе до `X-RateLimit-Reset` (не меньше 1 с), иначе 60 с. До 3 пауз; пауза дольше 5 минут не выдерживается — сразу `rate_limited` |
| 403 без признаков лимита, 400, 410, 422 | `request_failed` без повторов |
| 404 | `not_found` |
| 401 | Работа прекращается, `{"error":"unauthorized"}`, код 3 |
| Тело не является JSON-массивом или элемент не того вида | `invalid_response` |
| 304, хотя `If-None-Match` не отправлялся | `invalid_response` (нарушение контракта) |
| `Link: next` указывает на уже запрошенную страницу | `invalid_response`, а не бесконечный цикл |

Паузы прерываются по Ctrl+C. Предел в 5 минут выбран потому, что первичный лимит GitHub сбрасывается раз в час, а ждать час в интерактивном запуске хуже, чем честно сообщить `rate_limited` с временем до сброса в stderr.

### Формат кэша

Один файл на адрес запроса: `<cache-dir>/<sha256(url)>.json`.

```json
{
  "url": "https://api.github.com/repos/cli/cli/issues?state=open&sort=created&direction=asc&per_page=100",
  "etag": "W/\"8ddb46721c422fc2f8296e048a6dd17aebeb6b6ef67e19dc394b0e98e3898299\"",
  "link": "<https://api.github.com/repositories/212613049/issues?...&page=2>; rel=\"next\", <...>; rel=\"last\"",
  "body": [ ... ]
}
```

- Кэшируется только ответ 200 с заголовком `ETag` и корректным JSON-массивом. При повторном запросе того же адреса отправляется `If-None-Match`; на 304 тело берётся из кэша, в журнале `from_cache: true`; на 200 запись перезаписывается.
- Кроме ETag и тела хранится заголовок `Link`: GitHub не обязан повторять его в ответе 304, и без сохранённого `Link` пагинация из кэша оборвалась бы на первой странице.
- Заголовки запроса не хранятся, поэтому токена в кэше нет. Разные базовые адреса не пересекаются: адрес входит в ключ.
- Запись атомарная (временный файл + `rename`). Повреждённый файл — промах кэша, запрос уходит без `If-None-Match`. Ошибка записи кэша — предупреждение в stderr, работа продолжается.

### Журнал `--trace`

Одна строка JSON на каждую попытку HTTP-запроса, в порядке выполнения, сразу на диск (без буферизации):

```json
{"ts":"2026-10-25T13:42:59Z","method":"GET","url":"https://api.github.com/repos/cli/cli/issues?state=open&sort=created&direction=asc&per_page=100","status":200,"attempt":1,"from_cache":false,"error":null}
{"ts":"2026-10-25T13:43:09Z","method":"GET","url":"https://api.github.com/repos/cli/cli/issues?state=open&sort=created&direction=asc&per_page=100","status":304,"attempt":1,"from_cache":true,"error":null}
```

`status` — код ответа, `0` если ответа не было. `attempt` начинается с 1 для каждого адреса: повтор того же адреса увеличивает его, новая страница или переход по редиректу начинают с 1. `error` описывает только сбой транспорта (`"timeout"`, `"network"`); у полученного ответа `error: null`, а код виден в `status`. Заголовков в журнале нет.

## Тесты

```bash
cd service
go test -race ./...
gofmt -l .        # пусто
go vet ./...
```

Полная проверка в Linux на Go 1.22 — минимальной версии из задания. Локальный более новый тулчейн принял бы API стандартной библиотеки новее 1.22, несмотря на `go 1.22` в `go.mod`:

```bash
scripts/check-ghreport.sh
```

Тесты используют только `testing` и `net/http/httptest`, без реальной сети и реальных пауз. Покрыто: все ошибки аргументов; маппинг полей, фильтр PR (в том числе `"pull_request": null`), `--since` на границе суток и с часовыми поясами, дедупликация, остановка на `--limit` посреди страницы и без запроса лишних страниц; разбор `Link` (13 вариантов); повторы (паузы `[1s 2s]`, `[1s 2s 4s]`, обрыв соединения, таймаут, отмена); лимиты (`Retry-After`, `X-RateLimit-Reset`, сообщение, исчерпание пауз, длинная пауза, 429 без признаков); кэш (повторный запуск с 304, `Link` из кэша, слабый ETag, смена ETag, повреждённая запись, 304 без условного запроса, отсутствие токена в файлах); перенаправления (5 кодов, цикл, токен не уходит на другой хост); `run` целиком (коды 0/1/3, `--out`, отсутствие токена во всех выходах). Сквозная проверка против тестового сервера — в `api_tests/`.

## Принятые решения

| # | Вопрос | Решение |
|---|---|---|
| G1 | Повторы в `--repos` | Удаляются по точному совпадению строки (отчёт показывает имя как в аргументе) |
| G2 | Неизвестный или повторённый флаг, лишний аргумент | Код 2. `-h`/`--help` — справка в stderr, код 0. Разбор флагов свой: пакет `flag` молча берёт последний из повторённых флагов и пишет ошибки по-английски |
| G3 | Язык сообщений об ошибках аргументов | Русский, как в примере задания; журнал диагностики — английский |
| G5 | `--out <файл>` | Атомарная запись, stdout пуст. Фатальный объект всегда в stdout, файл отчёта при этом не создаётся |
| G6 | Некорректный `GITHUB_API_BASE_URL` | Код 2 |
| G12 | Повторы при лимите | До 3 пауз, пауза больше 5 минут не выдерживается |
| G13 | 403 без признаков лимита и прочие 4xx | `request_failed` без повторов |
| G15 | `Link` в ответе 304 | Если его нет, используется сохранённый в кэше |
| G18 | Поле `error` журнала | Только сбои транспорта; у полученного ответа `null` |
| G22 | Не удалось записать файл отчёта | Сообщение в stderr, код 1 |
| G23 | 401 после успешных репозиториев | Работа прекращается, только `{"error":"unauthorized"}`, код 3 |
| G24 | `--limit` и сортировка | Лимит в порядке выдачи, сортировка после |
